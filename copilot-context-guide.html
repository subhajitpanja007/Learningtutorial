Do and don't

Do

  • Decide in Microsoft 365, build in VS Code, and pass files between them, not conversations.
  • Ask Copilot Chat for Markdown with fixed headings when the output will reach the repository.
  • Store decisions in the repository and add one AGENTS.md row: "Implementing a decided change: read docs/decisions/".
  • Send pull request descriptions, not diffs, back to Microsoft 365 for announcements and runbooks.
  • Use anonymized sample rows in both tools.

Don't

  • Paste a whole Teams thread into Copilot in VS Code: it stays in the history of every later round.
  • Ask Copilot Chat to write PySpark for the repository: it cannot see AGENTS.md, your code or your tests.
  • Keep the decision only in a chat: Copilot in VS Code and new teammates cannot find it.
  • Copy the same rules into a Word document and AGENTS.md: they drift apart.
  • Paste secrets, connection strings or production extracts into either tool.

Set it up once

Repository

  • Create docs/decisions/ with a template: Decision, Mapping or details, Scope, Owners.
  • Add the AGENTS.md row that points to docs/decisions/ for decided changes.
  • Use a pull request skill whose Summary section is written for non-engineers.

Microsoft 365

  • Keep the two prompts (requirements summary, announcement) in a shared Copilot Page or document.
  • Keep the decision-record template in the same place so outputs match the repository format.

Teams (optional, preview)

  • Install the GitHub app once per team; each person connects their GitHub account.
  • Set a default repository per channel with @GitHub settings.
  • Only people with write access can trigger changes; in channels, pull requests are created under the app identity.

6# Iceberg MERGE upsert
7
8## Steps
91. Confirm the target table, the business key, and the column that orders versions (usually `updated_at`).
102. Deduplicate the batch to one row per key with `row_number()` over the key, newest first.
113. Write the MERGE from the template below.
124. If the table is partitioned by a column that never changes for a key (for example `days(event_ts)`),
13 add that column to the ON clause so Spark can prune files.
145. Add or update a unit test for the deduplication, then run `pytest -q -m "not integration"`.
15
16## Template
17```sql
18MERGE INTO {target} AS t
19USING {source_view} AS s
20ON t.{key} = s.{key}
21WHEN MATCHED AND s.updated_at > t.updated_at THEN UPDATE SET *
22WHEN NOT MATCHED THEN INSERT *
23```
24
25## What not to do
26- Do not MERGE a batch that still has duplicate keys: Spark fails when several source rows match one target row.
27- Do not remove the `s.updated_at > t.updated_at` guard: a rerun would overwrite newer data with older data.
28- Do not add a column that can change (such as `status`) to the ON clause: it creates duplicate rows.
29- Do not replace an upsert with `INSERT OVERWRITE` on a production table.
30- Do not `collect()` the batch to look for duplicates; use `groupBy(key).count().filter("count > 1")`.

Principles

  • Keep topics, not text

    AGENTS.md names each topic in one line and says where the details live. The agent opens a detail file only when its task needs it.

  • Say when to read

    A "Read when" column turns a list of links into a decision the model can make: editing jobs/ means open the PySpark conventions, nothing else.

  • Point to headings

    Name the file and the section, for example docs/architecture.md, section "Write path". Agents search by heading text, and small focused files are cheaper to read than one long file.

  • One fact, one home

    Every rule lives in exactly one file. Other files link to it. Duplicates drift apart and cost tokens twice.

  • Keep the few rules that apply everywhere

    Commands, the high-level layout, and three to five rules that matter on every task. Everything else is a reference.

  • Add rules when the agent makes a mistake

    Start small. When Copilot gets something wrong twice, add one line (or a "What not to do" entry in a skill). Every line should fix a real problem.

What a link actually does in VS Code

  • A Markdown link does not load anything by itself. The model sees the link text and decides whether to open the file with its read tool.
  • VS Code can attach linked files automatically when chat.includeReferencedInstructions is on. It is off by default (Local agent only). When on, it follows links in .github/copilot-instructions.md and in instruction files already in context, and attaches linked instruction files and workspace files. Leave it off if you want a router.
  • VS Code already lists every *.instructions.md file (path, description, applyTo) and every skill (name, description) in a short index. A good description is therefore your cheapest router in Copilot.
  • Other agents (Codex, Gemini CLI, Claude Code) do not read that index, so keep the "Read when" table in AGENTS.md for them and for new teammates.

# AGENTS.md

## About This Project

Welcome to the Orders Lakehouse project! This repository contains all of the code for our company's data
platform, which is used to ingest, transform and serve order data for analytics, reporting, finance and
machine learning use cases across the whole organization. The platform was started in 2023 and has grown
significantly since then. It is very important that all code in this repository is high quality, well
tested and follows our standards. Please read this entire file carefully before making any changes.

Apache Iceberg is an open table format for huge analytic datasets. It brings the reliability and simplicity
of SQL tables to big data, while making it possible for engines like Spark, Trino, Flink and Hive to safely
work with the same tables at the same time. Apache Spark is a unified analytics engine for large-scale data
processing, and PySpark is the Python API for Apache Spark.

We use PySpark for batch jobs and Apache Iceberg tables in three layers: bronze, silver and gold.

## PySpark Rules

- Always use MERGE INTO for upserts into Iceberg tables. Never use INSERT OVERWRITE on production tables.
- Deduplicate the source DataFrame by the business key before MERGE INTO, keeping the latest updated_at.
- Do not use collect() or toPandas() on large DataFrames.
- Prefer built-in functions over Python UDFs.
- Define schemas explicitly with StructType for landing data.
- Filter on partition columns early so that Iceberg can prune files.
- Build the Spark session with jobs.common.spark.build_spark().

## Iceberg Tables

- Always use MERGE INTO for upserts. Never use INSERT OVERWRITE on production tables.
- New tables must use format-version 2.
- Use hidden partitioning such as days(event_ts) and bucket(16, customer_id).
- Change schemas with ALTER TABLE instead of recreating tables.

When you create a table, follow this full example:

```sql
CREATE TABLE IF NOT EXISTS lake.silver.orders (
    order_id     BIGINT,
    customer_id  BIGINT,
    status       STRING,
    amount       DECIMAL(12, 2),
    event_ts     TIMESTAMP,
    updated_at   TIMESTAMP
)

TBLPROPERTIES (

    'write.merge.mode'  = 'merge-on-read',
```

## Example Upsert Job

Every upsert job should look like this:

```python
from pyspark.sql import SparkSession, Window
from pyspark.sql import functions as F

from jobs.common.spark import build_spark


def latest_per_order(df):
    window = Window.partitionBy("order_id").orderBy(F.col("updated_at").desc())
    return df.withColumn("_rn", F.row_number().over(window)).filter("_rn = 1").drop("_rn")


def main():
    spark = build_spark("clean_orders")
    raw = spark.table("lake.bronze.orders_raw").filter(F.col("ingested_at") >= F.date_sub(F.current_date(), 1))
    latest_per_order(raw).createOrReplaceTempView("orders_updates")
    spark.sql("""
        MERGE INTO lake.silver.orders AS t
        USING orders_updates AS s
        ON t.order_id = s.order_id
        WHEN MATCHED AND s.updated_at > t.updated_at THEN UPDATE SET *
        WHEN NOT MATCHED THEN INSERT *
    """)
    spark.stop()


if __name__ == "__main__":
    main()
```

## Table Maintenance Procedure

Every week, run these steps for every silver and gold table:

1. Compact small files: `CALL lake.system.rewrite_data_files(table => 'silver.orders')`
2. Compact delete files: `CALL lake.system.rewrite_position_delete_files(table => 'silver.orders')`
3. Rewrite manifests: `CALL lake.system.rewrite_manifests(table => 'silver.orders')`
4. Expire snapshots older than 7 days but keep the last 10:
   `CALL lake.system.expire_snapshots(table => 'silver.orders', older_than => TIMESTAMP '...', retain_last => 10)`
5. Look for orphan files with a dry run first:
   `CALL lake.system.remove_orphan_files(table => 'silver.orders', dry_run => true)`
6. Record the before and after file counts in the maintenance log.

      Prompts that save tokens

      Instead of

      Fix the orders job.

      Try

      In #file:jobs/silver/clean_orders.py, MERGE fails with MERGE_CARDINALITY_VIOLATION on yesterday's batch. Use the iceberg-merge-upsert skill. Fix the deduplication and run pytest -q -m "not integration".

      Names the file, the error and the skill, so the agent reads one file instead of searching.

      Instead of

      Why is Spark slow? [pasted 3,000 lines of logs]

      Try

      This MERGE takes 40 minutes. Here is the physical plan from df.explain("formatted") [paste only the plan]. The table is partitioned by days(event_ts). What prevents file pruning?

      A plan excerpt is a few hundred tokens; a full log is thousands and mostly noise.

      Instead of

      Look at the whole codebase and add sales_channel everywhere.

      Try

      /plan Add sales_channel to silver.orders: DDL, the silver job, tests. Read docs/architecture.md first.

      Planning with the map avoids a broad search and rework.

      Instead of

      Here is our full orders CSV. Write the schema.

      Try

      Here are 5 sample rows and the column list [paste]. Write the StructType for the landing schema.

      Five rows show the shape. Full data files waste tokens and may expose data.

      Token habits during a chat

      • One task per chat. Start a new chat when the task changes, or use /compact to summarize a long one.
      • Attach exact files with #file instead of broad searches when you already know where the code is.
      • Name the skill in your prompt (/iceberg-merge-upsert) when you know it applies.
      • Use Plan for multi-file changes: one short plan costs less than an agent that explores and redoes work.
      • Let subagents do exploration: their search results stay in their own context, not in your main chat.
      • Paste excerpts (a plan, a stack trace, five rows), never whole logs or data files.
      • Keep always-on files small, keep chat.includeReferencedInstructions off, and do not load CLAUDE.md twice.
