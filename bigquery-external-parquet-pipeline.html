01 — Definition

What is a BigQuery external table?

An external table is a BigQuery table object that contains only a definition — the file format, an optional schema, and a list of Cloud Storage URIs. The data itself stays where it is. When you query it, BigQuery reads the underlying files at query time. Google’s docs describe this as working with data stored outside of BigQuery.

DEFINITION-ONLY

The table stores metadata (format + URIs), not bytes. Your Parquet never moves out of gs://.

SCHEMA-ON-READ

Parquet is self-describing, so BigQuery auto-detects columns and types at query time.

READ-ONLY

BigQuery treats external data as read-only. No DML — the files remain the source of truth.

PERMANENT OR TEMPORARY

Permanent tables live in a dataset and can be shared. Temporary (session) tables exist only for one query.

05 — Format comparison

External Iceberg table vs external BigQuery table

Both are external and both are read-only, but they learn about your data in completely different ways. A plain external table lists files; an Iceberg external table reads a table manifest. That’s why Iceberg gets snapshots, schema evolution and consistent reads. A third option — BigLake tables for Apache Iceberg in BigQuery — is fully managed and writable, and is distinct from Iceberg external tables.

YOUR CASE

You write plain Parquet with PySpark, so a BigLake external table over Parquet is the right starting point — no Iceberg needed.

MOVE TO ICEBERG IF…

You need row-level updates/deletes, snapshot isolation, or schema/partition evolution in the lake itself.

GO MANAGED IF…

You want BigQuery to write the open-format table while Spark still reads it. That’s the managed Iceberg option.

iceberg_external_table.sql
-- Read-only Iceberg external table from a metadata JSON file
CREATE EXTERNAL TABLE `myproject.raw_zone.events_iceberg`
WITH CONNECTION `myproject.us-central1.my_gcs_conn`
OPTIONS (
  format = 'ICEBERG',
  uris   = ['gs://my-raw-bucket/warehouse/events/metadata/v2.metadata.json']
);

-- Query it exactly like a standard table
SELECT * FROM `myproject.raw_zone.events_iceberg` LIMIT 100;

With the JSON-metadata method you must update the metadata file reference whenever the table changes. Using BigLake metastore as the catalog avoids that manual step — which is why Google recommends it on Google Cloud.

07 — Build it

Step by step, with the entire code

Steps 1–2 are context (already done in your PySpark project). Step 3 is the fastest path. Steps 4–7 make it governed and cached. Steps 8–9 build the analysis layer. Every block has a copy button.

1
Land Parquet in the raw zonealready implemented
PySpark▶

Partition by a date column so BigQuery can prune later.

write_raw_zone.py
# PySpark — write on-prem data to the GCS raw zone as partitioned Parquet
(df.write
   .mode("overwrite")
   .partitionBy("dt")                 # yields dt=2026-01-01/ folders (Hive layout)
   .parquet("gs://my-raw-bucket/events/"))
2
Enable APIs, check location, create datasetcolocation is mandatory
setup▶

The bucket region and the dataset location must match — a bucket in us-central1 needs a dataset in us-central1 or the US multi-region. Dataset location is immutable afterwards.

shell
# Enable the required APIs
gcloud services enable \
  bigquery.googleapis.com \
  bigqueryconnection.googleapis.com \
  storage.googleapis.com

# Check the bucket region
gcloud storage buckets describe gs://my-raw-bucket --format="value(location)"

# Create a colocated dataset
bq --location=us-central1 mk --dataset \
  --description="Raw zone external tables" \
  myproject:raw_zone
3
Create a plain external tablefastest path — no connection needed
core▶

Parquet is self-describing, so omit the schema — it’s auto-detected. Four ways to do the same thing:

-- Permanent external table over Parquet in the raw zone
CREATE OR REPLACE EXTERNAL TABLE `myproject.raw_zone.events_ext`
OPTIONS (
  format = 'PARQUET',
  uris   = ['gs://my-raw-bucket/events/*.parquet']
);

-- Query it like any table
SELECT COUNT(*) FROM `myproject.raw_zone.events_ext`;
# Build a table definition, then create the table
bq mkdef --source_format=PARQUET \
  "gs://my-raw-bucket/events/*.parquet" > /tmp/def.json

bq mk --table \
  --external_table_definition=/tmp/def.json \
  myproject:raw_zone.events_ext

# Temporary (session) table — nothing stored in a dataset
bq query --external_table_definition=events::/tmp/def.json \
  'SELECT COUNT(*) FROM events'
from google.cloud import bigquery

client = bigquery.Client()

ec = bigquery.ExternalConfig("PARQUET")
ec.source_uris = ["gs://my-raw-bucket/events/*.parquet"]
ec.autodetect  = True

table = bigquery.Table("myproject.raw_zone.events_ext")
table.external_data_configuration = ec
client.create_table(table)
resource "google_bigquery_table" "events_ext" {
  dataset_id = "raw_zone"
  table_id   = "events_ext"

  external_data_configuration {
    autodetect    = true
    source_format = "PARQUET"
    source_uris   = ["gs://my-raw-bucket/events/*.parquet"]
  }
}
4
Declare Hive partitionsprune by dt so queries don’t scan the whole lake
core▶

Declaring the partition column lets BigQuery skip irrelevant folders. Requiring a filter guards against accidental full scans.

GoogleSQL
CREATE OR REPLACE EXTERNAL TABLE `myproject.raw_zone.events_ext`
WITH PARTITION COLUMNS (
  dt DATE                                -- parsed from dt=YYYY-MM-DD/ path
)
OPTIONS (
  format = 'PARQUET',
  uris   = ['gs://my-raw-bucket/events/*'],
  hive_partition_uri_prefix     = 'gs://my-raw-bucket/events',
  require_hive_partition_filter = true
);
5
Create a Cloud resource connectionprerequisite for the BigLake upgrade
upgrade▶

The connection carries a Google-managed service account. Grant that account read on the bucket, so analysts need rights only on the table.

shell
# 1. Create the connection (location must match dataset + bucket)
bq mk --connection \
  --location=us-central1 \
  --project_id=myproject \
  --connection_type=CLOUD_RESOURCE \
  my_gcs_conn

# 2. Read back its service account id
bq show --connection myproject.us-central1.my_gcs_conn
# -> bqcx-....@gcp-sa-bigquery-condel.iam.gserviceaccount.com

# 3. Let that service account read the raw zone
gcloud storage buckets add-iam-policy-binding gs://my-raw-bucket \
  --member="serviceAccount:bqcx-....@gcp-sa-bigquery-condel.iam.gserviceaccount.com" \
  --role="roles/storage.objectViewer"
6
Create the BigLake tableWITH CONNECTION + metadata caching
upgrade▶

Same Parquet, now with access delegation and metadata caching. Staleness accepts an interval between 30 minutes and 7 days; 0 (the default) disables caching.

GoogleSQL
CREATE OR REPLACE EXTERNAL TABLE `myproject.raw_zone.events_biglake`
WITH CONNECTION `myproject.us-central1.my_gcs_conn`
OPTIONS (
  format = 'PARQUET',
  uris   = ['gs://my-raw-bucket/events/*.parquet'],
  max_staleness       = INTERVAL 4 HOUR,   -- 30 min … 7 days
  metadata_cache_mode = 'AUTOMATIC'
);

-- Force a refresh on demand (needed for MANUAL mode)
CALL BQ.REFRESH_EXTERNAL_METADATA_CACHE('myproject.raw_zone.events_biglake');
7
Query the raw datapartition pruning + aggregation
core▶

Ordinary GoogleSQL. The WHERE dt … filter triggers pruning so only relevant Parquet is scanned.

GoogleSQL
SELECT
  dt,
  COUNT(*)          AS events,
  COUNT(DISTINCT user_id) AS users,
  SUM(amount)       AS revenue
FROM `myproject.raw_zone.events_biglake`
WHERE dt BETWEEN '2026-01-01' AND '2026-01-31'   -- prunes partitions
GROUP BY dt
ORDER BY dt;
8
Promote to a native curated tableunlocks DML, clustering, snapshots, BI Engine
analysis▶

This single pattern removes almost every external-table limitation. Partition and cluster the destination for real performance.

GoogleSQL
-- One-off build of the curated native table
CREATE OR REPLACE TABLE `myproject.curated.events`
PARTITION BY DATE(event_ts)
CLUSTER BY user_id, region
AS SELECT * FROM `myproject.raw_zone.events_biglake`;

-- Incremental top-up (schedule this)
MERGE `myproject.curated.events` T
USING `myproject.raw_zone.events_biglake` S
ON T.event_id = S.event_id
WHEN NOT MATCHED THEN INSERT ROW;
9
Add a governed serving layerviews, materialized views, security
analysis▶

Materialized views over a BigLake table require metadata caching enabled and a max_staleness greater than the base table’s.

GoogleSQL
-- Materialized view over the BigLake table (base staleness = 4 HOUR)
CREATE MATERIALIZED VIEW `myproject.mart.events_daily`
OPTIONS (max_staleness = INTERVAL 8 HOUR)
AS SELECT dt, region, COUNT(*) AS events
FROM `myproject.raw_zone.events_biglake`
GROUP BY dt, region;

-- Row-level security on the curated table
CREATE ROW ACCESS POLICY eu_only
ON `myproject.curated.events`
GRANT TO ("group:eu-analysts@example.com")
FILTER USING (region = "EU");
